## 🔴 packed-refs 坑复发 —— 找到真根因并彻底修掉

08-30 那次只写 loose ref，**修法不彻底**。本次 push 后问题复发：
push 明确报告 `4ab0bff..a9d54bc main -> main` 成功，
但 `git rev-parse origin/main` 又读回远古的 `e693512`，`git status` 误报 ahead 10。

### 排查过程（排除了几个错误假设）

| 假设 | 验证结果 |
|---|---|
| `.git` 或 packed-refs 不可写 | ❌ 排除，两者都可写 |
| 用了 reftable 后端导致旧文件失效 | ❌ 排除，`extensions.refstorage` 未设置、无 `.git/reftable` |
| OneDrive 同步回滚文件 | ❌ 排除，`$OneDrive` 未设置，项目不在同步范围 |
| 自定义 hook 干扰 | ❌ 排除，四个 hook（post-checkout/commit/merge、pre-push）是 Git LFS 标准安装 |
| 写入根本不生效 | ❌ 排除，实测写 loose ref 立刻能读回 |

**真根因**：`.git/packed-refs` 这个文件**长期没被任何 git 操作重写过** ——
mtime 一直停在 `Apr 20 21:43`，期间所有 fetch/push 都没能更新它。
而 08-30 手工写的 loose ref 在后续 push 过程中被清理掉，
陈旧的 packed-refs 记录重新浮出水面 → 问题复发。

### 彻底修法（已验证）

```bash
REAL=$(git ls-remote origin refs/heads/main | cut -f1)
mkdir -p .git/refs/remotes/origin
printf '%s\n' "$REAL" > .git/refs/remotes/origin/main   # 临时纠正
git pack-refs --all                                      # 关键一步
```

`git pack-refs --all` 成功重写了 packed-refs（mtime 终于变成 `2026-09-06 00:10:38`），
陈旧记录被彻底替换。之后 `fetch` 幂等、三值（HEAD / origin/main / ls-remote）完全一致。

**教训**：只写 loose ref 是治症状；必须跟一次 `git pack-refs --all` 才是治根。
已把正确修法更新进 MEMORY.md（替换掉 08-30 那个不彻底的版本）。

### ❌ 上面那个 pack-refs 结论是错的 —— 继续挖到真根因

`pack-refs --all` 之后又 push 了一次，问题**立刻第三次复发**。说明它只是碰巧把
当时的值写进了 packed-refs，并没有修好写入路径，而且它会顺手删掉 loose ref 和
`refs/remotes/origin/` 目录，反而让下一次 push 无处可写。

### 真根因：git 的 ref 写入路径坏了（不是 packed-refs 陈旧）

用 `find .git -newer <marker>` 取证，执行 `git update-ref` 后磁盘上
**只有 `.git/logs/refs/remotes/origin/main`（reflog）被写入**，
ref 本身既没写 loose、也没写 packed。

`GIT_TRACE_REFS=1` 显示事务 `finish: 0`（成功），但旧值报告为全 0
—— git 自己认为 ref 不存在，与 `for-each-ref` 读到的 a9d54bc 直接矛盾。
reflog 里累积了三条"a9d54bc → f4ba835"的成功记录，而 ref 从未落地。

**逐一排除的假设**：

| 假设 | 验证方式 | 结果 |
|---|---|---|
| `.git`/packed-refs 不可写 | touch + 追加写测试 | ❌ 都可写 |
| READONLY / HIDDEN 属性异常 | Python 读 `st_file_attributes` | ❌ 正常 |
| reftable 后端使旧文件失效 | `extensions.refstorage` + `.git/reftable` | ❌ 未启用 |
| OneDrive 同步回滚 | `$OneDrive` 环境变量 | ❌ 项目不在同步范围 |
| 自定义 hook 干扰 | 列 `.git/hooks/` | ❌ 4 个是 Git LFS 标准安装 |
| WorkBuddy 沙箱拦截写入 | `dangerouslyDisableSandbox` 重测 | ❌ 无沙箱同样失败 |
| junction / reparse point | 检查 `FILE_ATTRIBUTE_REPARSE_POINT` | ❌ 无 |
| `.lock` + rename 机制被拦 | shell 手工模拟同样操作 | ❌ shell 做完全正常 |

结论：git 2.55.0.windows.3 在本仓库的 ref 写入存在缺陷（或 ref 存储局部损坏）。
**shell 直写可靠，git 自己的 ref 命令不可靠。**

### 最终修法（写入 MEMORY.md）

shell 直写 loose ref **并同步修正 packed-refs 两条记录**（本地分支那条也是陈旧的
a9d54bc，是个潜在雷：loose ref 一旦被清理，本地分支会看起来倒退）。
**明确禁用 `git pack-refs --all`**。

修完校验：三值一致 ✅、`git fetch` 幂等 ✅、`git fsck` 零报错 ✅。
